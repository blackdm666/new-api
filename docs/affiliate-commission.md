# 推荐计划充值返佣架构

## 业务边界

- 只计算一级邀请关系，不做多级分销。
- 当前只计算 E支付渠道完成的钱包充值订单；Stripe、订阅购买、佣金转余额、赠送额度、兑换码和管理员手工调额均不产生佣金。
- 推广等级直接绑定 NewAPI 用户组：`default` 用户组代表初级推广，`高级推广` 用户组代表高级推广，`金牌推广` 用户组代表金牌推广，默认返佣比例分别为 5%、10%、15%。
- 人工审核模式下，充值成功后先生成待审核佣金，管理员审核通过后才增加邀请人的可用佣金额度；自动审核模式下，合法充值产生的佣金会在同一事务中直接通过并计入可用佣金。
- 返佣比例、邀请人分组和推广等级在充值成功时快照，后续调整分组不会追溯改变历史订单。
- 功能默认关闭；首次启用时记录正式启用时间，早于该时间的历史订单和重复回调不会补建佣金。
- E支付使用验签回调中的实付金额，并与下单金额按分核对；金额不一致时拒绝入账，避免错误充值和错误返佣。

## 数据模型

### `affiliate_commissions`

每个成功充值订单最多对应一条佣金记录，`top_up_id` 使用唯一索引保证支付回调重试不会重复返佣。记录保存：

- 邀请人、受邀用户和充值订单；
- 充值实付金额、当时的分组、等级和返佣比例；
- 佣金金额及换算后的 NewAPI 额度；
- 待审核、已通过、已驳回状态；
- 审核管理员、审核时间和驳回原因。

### `affiliate_upgrade_notices`

升级提醒使用独立 outbox 表。`inviter_id + threshold` 唯一索引保证同一阶段只产生一封提醒；提醒保存触发时的有效人数和有效充值金额快照，发送前会重新核对功能开关、当前分组、实时人数、实时金额和当前配置比例。失败按指数退避重试，最多 8 次后进入失败列表，管理员可以人工重发；发送任务使用租约避免多进程重复投递。

### `affiliate_payouts`

现金结算申请独立保存，不复用充值订单：

- 最低结算金额为 ¥100，用户可随时提交；
- 提交时在同一事务中从可用佣金扣除并冻结申请金额，避免同时转入 API 余额或重复申请；
- 用户只能撤回待审核申请，管理员驳回或用户撤回后原额度自动退回；
- 管理员可随时审核，系统以每月 10 日作为计划打款日；审核通过后可选择手动打款或支付宝直接打款；
- 手动打款只需二次确认，不要求录入外部流水号，系统自动生成内部审计编号；
- 支付宝直接打款采用“已审核 → 支付宝处理中 → 已打款”状态机。同一笔处理中申请始终复用同一个商户业务号并优先查询，响应不明确时禁止再次发起，避免重复付款；
- 支付宝明确失败时申请回到已审核状态并保留失败信息，管理员修正配置或收款资料后可以重新发起；
- 收款账号使用系统敏感数据密钥加密保存，列表读取时才解密；
- `request_id` 使用唯一索引，前端重试不会重复冻结佣金。

生产环境必须持久化并保持 `CRYPTO_SECRET` 不变；更换该密钥会导致历史收款账号无法解密。

### `affiliate_transfers`

佣金转入 API 余额使用独立、不可变的审计流水，不复用充值订单。每条记录保存用户、幂等请求号、人民币佣金金额、转入额度、转入前后的可用佣金和 API 余额快照及创建时间。余额变动和流水创建在同一个数据库事务内完成；`request_id` 使用唯一索引，同一请求重试只返回原流水，若同一个请求号携带了不同金额则明确拒绝，不会重复扣除佣金。

该流程不创建 `top_ups` 充值订单，也不创建 `affiliate_commissions` 返佣记录，因此佣金转入 API 余额不会再次触发邀请返佣。管理员可以在“推广管理 → 余额转入记录”按用户名、UID、记录 ID 或请求 ID 检索完整流水。

### `affiliate_accounts`

现金佣金使用独立的人民币分账，不再读写 NewAPI 原有的 `users.aff_quota`：

- `available_cents` 保存可转余额或可申请结算的佣金；
- `frozen_cents` 保存已提交结算但尚未完成或退回的佣金；
- `lifetime_earned_cents` 保存历史累计审核通过佣金；
- 固定按站点当前 1:1 规则转入 API 余额，并同时保存人民币金额和额度快照；
- 旧 `aff_quota` 仅保留为历史固定邀请 API 奖励，不能作为现金提现。

### `email_deliveries`

NewAPI 原有的邮箱验证、密码重置和系统通知，以及推荐计划的佣金审核、等级升级与结算状态邮件，统一进入持久化 SMTP 发件箱。业务先写入数据库，再由主节点投递；失败按指数退避最多重试 8 次，达到上限后进入“系统设置 → 邮件模板 → 邮件投递失败”，Root 修复 SMTP 后可人工重试。业务邮件使用稳定事件键防止重复发送；已送达或已过期邮件会清空收件人、主题和正文，只保留必要审计元数据。

## 资金与并发约束

1. 支付渠道回调锁定充值订单。
2. 在同一数据库事务中把订单改为成功、增加受邀用户余额并创建佣金流水；人工模式保存为待审核，自动模式保存为已通过并立即增加邀请人的可用佣金。
3. 重复回调发现订单已经成功时，只在订单不早于正式启用时间时幂等补建缺失记录，不再次增加余额。
4. 审核通过时重新锁定佣金和原充值订单，核对订单状态、用户、订单号及实付金额。
5. 只有仍为待审核的记录可以完成审核；拒绝必须填写原因，并发审批只允许一个事务成功入账。
6. 返佣属于支付后的附属业务：零佣金、邀请人不存在/已删除/已禁用时直接跳过；返佣子流程异常通过事务保存点隔离，不得回滚已验证的充值入账。

这组约束保证支付回调、人工审核和任务重试都不会导致重复入账。

`request_id` 是浏览器在用户提交“转入余额”或“申请结算”时生成的幂等请求号。网络超时、重复点击或客户端重试必须复用同一个请求号，后端因此只扣款一次并返回原结果；若同一个请求号却携带不同金额或不同收款资料，说明请求被错误复用，系统会明确拒绝而不是猜测用户意图。

## 等级和升级

- 新注册用户所在的 `default` 用户组按初级推广比例计算。
- 只有管理员审核升级并把用户组修改为目标推广组后，该用户后续产生的佣金才按新比例计算；达到门槛但尚未审核时，仍按当前用户组比例计算。
- 旧版本遗留的 `初级推广` 用户组和比例配置会在读取时兼容为 `default`，新配置不再要求单独建立初级推广用户组。
- 有效充值人数按至少存在一笔未驳回佣金记录的不同受邀用户计数。
- 有效充值金额按未驳回佣金记录中的充值实付金额累计，使用分为整数单位保存和比较。
- `default` 用户累计达到 50 位有效充值受邀用户，或累计有效充值金额达到 ¥2,000，满足任一条件即可进入高级推广审核；管理员通过后，用户组修改为 `高级推广`。
- `高级推广` 用户累计达到 500 位有效充值受邀用户，或累计有效充值金额达到 ¥20,000，满足任一条件即可进入金牌推广审核；管理员通过后，用户组修改为 `金牌推广`。人数和金额均按全部历史未驳回记录累计，不从升级为高级推广时重新计数。
- 每次达到当前等级的下一阶段任一门槛时，系统都会通过 NewAPI 共用 SMTP 向 Root 的系统通知邮箱发送升级提醒。升级不是自动执行，后台队列同时显示当前组、目标组、实时有效人数、实时有效充值金额和对应门槛。
- 每次审核请求必须携带队列中显示的目标用户组；重复请求或并发点击不能让同一用户连续跨越两个等级。
- 升级队列、提醒发送和管理员确认升级时都会重新核对两项实时条件；只有人数和金额都低于门槛时才不能升级。

## 权限

- 普通用户：查看自己的汇总、推广链接、佣金记录、余额转入流水和受邀用户统计；可将可用佣金转入主余额，也可提交、查询和撤回待审核的现金结算申请。
- 管理员：在“佣金流水”查看全部历史记录和最终状态，在“佣金审核”只处理待审核记录；可按关键词检索并通过或填写原因驳回记录；检索余额转入流水及前后余额快照；审核现金结算申请，并通过手动确认或支付宝接口完成打款；处理推广员升级；查看并重试升级通知失败项。
- Root：除审核能力外，还可以在“系统设置 → 计费设置 → 推荐返佣”中原子更新功能开关、自动审核开关、三个推广用户组比例和升级门槛，并配置支付宝自动打款；在“邮件模板”中维护多语言模板、查看投递死信并重试。自动打款只使用支付宝官方证书模式，需要应用私钥、应用公钥证书、支付宝公钥证书和支付宝根证书，系统自动计算并校验请求所需的证书序列号。审核模式切换只影响之后产生的佣金，不改写历史记录。

## 配置项

- `AffiliateCommissionEnabled`
- `AffiliateCommissionAutoApprove`（`false` 为人工审核，`true` 为自动审核；默认 `false`）
- `AffiliateCommissionDefaultRateBasisPoints`
- `AffiliateCommissionGroupRates`
- `AffiliateUpgradeEffectiveInviteesThreshold`
- `AffiliateGoldUpgradeEffectiveInviteesThreshold`
- `AffiliateUpgradeEffectiveTopUpAmountCents`
- `AffiliateGoldUpgradeEffectiveTopUpAmountCents`
- `AffiliateCommissionActivatedAt`（系统在首次启用时自动写入，不在界面手工设置）
- `AffiliateAlipayPayoutEnabled`
- `AffiliateAlipayAppId`
- `AffiliateAlipayPrivateKey`（使用 `CRYPTO_SECRET` 加密保存，接口不回传明文）
- `AffiliateAlipayAppCertificate`（使用 `CRYPTO_SECRET` 加密保存，接口不回传明文）
- `AffiliateAlipayPublicCertificate`（使用 `CRYPTO_SECRET` 加密保存，接口不回传明文）
- `AffiliateAlipayRootCertificate`（使用 `CRYPTO_SECRET` 加密保存，接口不回传明文）
- `AffiliateAlipayTransferTitle`

比例使用基点保存，`500 = 5%`，避免浮点数误差。旧的固定邀请奖励 `QuotaForInviter` / `QuotaForInvitee` 是另一套 API 额度规则；系统会在启用推荐计划时强制要求两项均为 0，旧用户已经获得的 `aff_quota` 不会导入现金佣金账户。

## 运维检查

- 待审核记录异常增长：检查管理员处理积压。
- 升级提醒长期未发送：在后台失败列表检查重试次数、下次重试时间和 `last_error`，确认 NewAPI 共用 SMTP 与 Root 系统通知邮箱可用。
- 支付成功但无佣金：核对邀请关系、邀请人是否仍有效、功能开关、正式启用时间、是否为钱包充值，以及 `top_up_id` 是否已有记录。
- 易支付回调失败：核对验签结果、回调 `money` 与本地订单金额是否按分一致。
- 比例争议：以佣金记录中的比例和分组快照为准，不使用用户当前分组回算历史订单。
- 支付宝打款长期处于处理中：先在结算管理点击“刷新打款状态”，不得手动确认或创建新业务号；核对支付宝开放平台订单状态后再处理。
- 支付宝打款配置异常：由 Root 在“系统设置 → 计费设置 → 推荐返佣 → 自动打款”填写同一应用的四份证书资料并测试凭据。测试只执行签名订单查询，不产生资金转移。`isv.missing-app-cert-sn` 表示应用公钥证书或支付宝根证书未正确参与签名请求。
- 系统邮件达到最大重试次数：Root 在“系统设置 → 邮件模板 → 邮件投递失败”查看收件人、类型和最后错误；修复共用 SMTP 后点击重试。
